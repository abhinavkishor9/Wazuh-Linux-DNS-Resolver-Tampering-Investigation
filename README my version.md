# Wazuh-Linux-DNS-Resolver-Tampering-Investigation
## Overview
### 1. Introduction

The Domain Name System (DNS) translates human-readable domain names into IP addresses. When a Linux system accesses a domain such as `example.com`, it relies on resolver configuration to determine how DNS queries should be handled.

DNS resolver configuration is therefore an important part of a system's network security.

If an attacker or unauthorized process changes the resolver settings, DNS queries may be sent to an unexpected server. This could influence how domain names are resolved and potentially redirect users or applications to untrusted infrastructure.

A SOC analyst must understand how resolver settings are managed, where configuration changes occur, and how those changes can be investigated.

### 2. Linux DNS Resolver Configuration

The primary resolver configuration file on many Linux systems is:

```text
/etc/resolv.conf
```

A typical configuration may contain:

```text
nameserver 192.168.1.1
nameserver 8.8.8.8
search example.local
options timeout:2 attempts:3
```

#### Important Directives

| Directive | Description |
|---|---|
| `nameserver` | Specifies the DNS server used for name resolution. |
| `search` | Defines domain suffixes used during name resolution. |
| `options` | Defines resolver behaviour, including timeouts and query attempts. |

The actual contents and management of this file depend on the Linux distribution and network configuration.

### 3. NetworkManager and DNS Management

NetworkManager can manage DNS configuration based on connection profiles, DHCP information, and other network settings.

It may generate or update `/etc/resolv.conf`.

On systems using NetworkManager, inspecting only the resolver file may not be sufficient. An analyst should also inspect the active connection and DNS settings.

Useful commands include:

```bash
nmcli device show
```

```bash
NetworkManager --print-config
```

```bash
cat /etc/resolv.conf
```

The analyst should determine whether the file is manually maintained, generated by NetworkManager, or managed through another resolver service.

### 4. systemd-resolved

Some Linux systems use systemd-resolved to provide local DNS resolution and manage DNS settings.

Its configuration may involve:

```text
/etc/systemd/resolved.conf
```

Runtime resolver information may be available under:

```text
/run/systemd/resolve/
```

The service can be checked using:

```bash
systemctl status systemd-resolved
```

If the service is not installed, that does not automatically indicate a problem. Another component, such as NetworkManager, may be responsible for DNS management.

### 5. What Is DNS Resolver Tampering?

DNS resolver tampering refers to an unauthorized or unexpected modification of DNS resolver settings.

An attacker with sufficient privileges may attempt to:

- Replace an approved DNS server with an untrusted server.
- Change DNS search domains.
- Modify resolver options.
- Alter NetworkManager connection profiles.
- Change resolver configuration to influence name resolution.
- Disrupt DNS resolution or redirect queries.

A suspicious resolver change should be investigated in the context of the host's expected network configuration.

### 6. Potential Security Impact

Unexpected DNS configuration changes can create several security risks.

#### DNS Redirection

A system may send DNS queries to a server that returns unexpected or manipulated responses.

#### Phishing and Impersonation

Manipulated name resolution may direct users or applications to infrastructure that imitates legitimate services.

#### Communication Through Untrusted DNS

DNS queries may be routed through an unexpected server, creating a visibility and trust concern.

#### Service Disruption

Incorrect resolver settings may prevent applications from resolving required internal or external domains.

These are potential impacts. A changed resolver configuration alone does not prove that any of these outcomes occurred.

### 7. Auditd for Resolver Change Monitoring

Auditd is the Linux auditing framework used to record selected system activities.

It can monitor file writes and attribute changes on important configuration paths.

For example:

```bash
sudo auditctl -w /etc/resolv.conf -p wa -k lab136_dns_resolver
```

The options mean:

| Option | Purpose |
|---|---|
| `-w` | Adds a watch for a path. |
| `-p w` | Monitors write access. |
| `-p a` | Monitors attribute changes. |
| `-k` | Assigns a searchable audit key. |

The audit key makes it easier to retrieve related records:

```bash
sudo ausearch -k lab136_dns_resolver -i
```

Auditd events may contain information about the executable, process, user identity, file path, system call, and operation result.

A watch must be configured for the correct file or directory. Changes made through another configuration mechanism or runtime-only interface may require additional monitoring.

### 8. File Integrity Monitoring

File integrity monitoring helps identify changes to important configuration files.

A SHA-256 hash can be calculated using:

```bash
sha256sum /etc/resolv.conf
```

A later hash can be compared against the baseline.

If the hash changes, the file contents have changed.

However, a hash does not identify the process or user responsible for the modification. It should be correlated with Auditd records, timestamps, file metadata, and system logs.

### 9. Wazuh Integration

Wazuh can collect and analyze security telemetry from monitored Linux systems.

For this investigation, Auditd provides the underlying file-operation evidence.

The general monitoring workflow is:

1. Auditd records a monitored operation.
2. Wazuh collects the relevant audit log.
3. Wazuh processes and decodes the event.
4. Matching detection rules may generate alerts.
5. An analyst reviews the event and correlates it with other evidence.

The presence of an Auditd record does not automatically prove that Wazuh generated an alert.

Collection, decoding, rule matching, and dashboard visibility should be validated separately.

### 10. DNS Resolution Validation

Two useful commands are:

```bash
getent hosts example.com
```

and:

```bash
dig example.com
```

`getent` checks name resolution through the system's configured name service mechanism.

`dig` performs a DNS query and provides useful details such as the response status, answer records, query time, and DNS server.

These commands help establish whether DNS resolution works at the time of testing.

Successful resolution does not independently prove that the configured DNS server is trusted or that no earlier tampering occurred.

### 11. Investigation Methodology

A DNS resolver investigation should follow a structured process:

1. Identify the operating system and DNS management component.
2. Record the current resolver configuration.
3. Inspect NetworkManager and other relevant configuration sources.
4. Establish file metadata and hash baselines.
5. Review existing Auditd rules before adding monitoring.
6. Monitor relevant configuration paths.
7. Investigate file-operation events.
8. Identify the user, process, and executable involved.
9. Compare the resulting DNS configuration with an approved baseline.
10. Validate DNS resolution and review supporting network and service logs.
11. Correlate available evidence in Wazuh.
12. Document confirmed findings, plausible explanations, and unknowns.

### 12. Important Investigation Principle

Not every DNS configuration change is malicious.

NetworkManager, DHCP clients, VPN software, and legitimate administrative operations can update DNS settings.

The analyst should establish:

- What changed?
- Which file or connection profile changed?
- Which user or process performed the operation?
- Was the change expected?
- Is the configured DNS server approved?
- Did the change affect DNS resolution?
- Is there supporting evidence of malicious activity?

The objective is not merely to detect a changed file. It is to determine whether the change was authorized, expected, and consistent with the system's normal network behaviour.

**Follow the evidence, not the assumption.**

This lab investigates Linux DNS resolver configuration and examines how unauthorized or unexpected changes to DNS settings can be detected using Auditd and Wazuh.

The investigation was performed on Rocky Linux 9.8 with NetworkManager managing the DNS configuration. The primary focus was `/etc/resolv.conf`, its configuration source, file integrity, and the audit telemetry generated by a controlled file modification.

The lab also examines why DNS resolver changes must be investigated in context. A configuration change alone does not establish malicious activity because NetworkManager, DHCP, VPN software, and other legitimate components may update DNS settings.

## Lab Scenario

### Scenario: Investigating Unexpected Linux DNS Resolver Changes

A Linux server is being reviewed as part of a routine security investigation. The security team wants to ensure that its DNS resolver configuration has not been modified in an unauthorized manner.

DNS configuration is security-relevant because the resolver determines which DNS servers receive queries from the system. An unexpected change could redirect DNS queries, interfere with name resolution, or introduce communication with an untrusted DNS service.

The analyst is asked to examine the current resolver configuration, identify which system component manages it, and determine whether the available monitoring can provide evidence of file modifications.

### Investigation Context

The investigation takes place on a Rocky Linux 9.8 system monitored through Wazuh and Auditd.

The analyst must first establish the system's normal DNS configuration rather than assuming that the resolver file is manually maintained.

The investigation should examine:

- The current contents and metadata of `/etc/resolv.conf`.
- The NetworkManager service and active DNS settings.
- The presence or absence of systemd-resolved.
- Existing Auditd rules and audit service health.
- The relationship between resolver settings and the active network interface.

Once the baseline is established, the analyst configures targeted Auditd monitoring and performs an isolated file-modification test.

### Investigation Challenge

The analyst must determine whether the monitoring system can identify a configuration-file write and provide useful attribution.

A controlled test file is used instead of modifying the active DNS resolver. This avoids interrupting the server's network connectivity while still allowing the analyst to examine file-operation telemetry.

The resulting audit records should be examined for the executable, process context, user identity, target file, and operation result. File hashes should also be compared to establish whether the test file contents changed.

The analyst must then validate DNS resolution and determine whether the observed resolver settings are consistent with the system's active network configuration.

### Expected Investigation Questions

1. Which component manages DNS configuration on the Linux system?
2. Is `/etc/resolv.conf` a regular file or a symbolic link?
3. Which DNS server is currently configured?
4. Does NetworkManager report the same DNS server?
5. Is systemd-resolved installed and active?
6. Can Auditd record a controlled configuration-file modification?
7. Which process and user context are associated with the operation?
8. Did the file hash change after the controlled modification?
9. Does DNS resolution work during validation?
10. Is there sufficient evidence to establish unauthorized resolver tampering?

### Investigation Boundaries

The investigation must preserve the active network configuration.

The analyst should not replace the configured DNS server, overwrite `/etc/resolv.conf`, restart NetworkManager unnecessarily, or introduce a real DNS redirection.

A separate test file should be used for the controlled modification. Existing Auditd rules must be inspected before adding lab-specific monitoring, and cleanup must remove only the rules created for this investigation.

### Expected Outcome

The analyst should be able to demonstrate how a monitored file modification can be identified through Auditd and how file integrity evidence can support an investigation.

The final assessment must distinguish between a successful controlled monitoring test and proof of an actual security incident.

A configuration change is not automatically malicious. Its origin, authorization, resulting DNS behaviour, and supporting evidence must be evaluated before drawing a conclusion.

**The investigation is successful when the analyst can explain what the evidence confirms, what remains unverified, and why.**

## Investigation Workflow

### 1. Establish the resolver baseline

Inspect the operating system, NetworkManager service, resolver file, and active DNS configuration.

```bash
cat /etc/os-release
sudo systemctl status NetworkManager --no-pager
ls -l /etc/resolv.conf
cat /etc/resolv.conf
NetworkManager --print-config
nmcli device show
```

### 2. Inspect audit services

Check Auditd status, current audit statistics, and existing rules before introducing lab-specific monitoring.

```bash
sudo systemctl status auditd --no-pager
sudo auditctl -s
sudo auditctl -l
```

### 3. Establish file integrity baseline

Record resolver file metadata and its SHA-256 hash.

```bash
sudo stat /etc/resolv.conf
sudo sha256sum /etc/resolv.conf
```

Recorded baseline SHA-256:

```text
237d02064a9c5e5cb59347ee894eb238a2ea82e94c81d84c2969859660569cd8
```

### 4. Configure targeted Auditd monitoring

The following watches were added:

```bash
sudo auditctl -w /etc/resolv.conf -p wa -k lab136_dns_resolver
sudo auditctl -w /etc/NetworkManager/ -p wa -k lab136_dns_resolver
```

The rules were verified with:

```bash
sudo auditctl -l | grep lab136_dns_resolver
```

### 5. Perform a controlled modification

A separate test file was created under `/var/tmp/lab136` to avoid modifying the active resolver configuration.

```bash
sudo mkdir -p /var/tmp/lab136
```

```bash
sudo tee /var/tmp/lab136/resolv.conf.test > /dev/null <<'EOF'
# Lab 136 controlled DNS resolver configuration test
nameserver 192.0.2.53
search lab136.invalid
EOF
```

A dedicated Auditd watch was added:

```bash
sudo auditctl -w /var/tmp/lab136/ -p wa -k lab136_dns_test
```

The initial SHA-256 was:

```text
7ece6d4f17e33c9662d6d9d9526817bfdf8ec78ae3365bc8eb4f8da43816b61e
```

A controlled comment was appended:

```bash
echo '# Lab 136 controlled modification' | sudo tee -a /var/tmp/lab136/resolv.conf.test
```

The resulting SHA-256 was:

```text
b26119a8e32d4c46be1d179ab63133db7122b3d7e42236f3c5628b9f3960f7fb
```

The hash difference confirmed that the test file contents changed.

### 6. Investigate Auditd events

The test event was reviewed using:

```bash
sudo ausearch -k lab136_dns_test -i
```

The successful modification event contained:

- Process: `tee`
- Executable: `/usr/bin/tee`
- Operation: `openat`
- Result: `success=yes`
- File: `/var/tmp/lab136/resolv.conf.test`
- Audit key: `lab136_dns_test`
- Login identity: `abhinavmathur`
- Effective user: `root`
- Timestamp: `13/11/26 07:42:59.738`

The event confirms a successful controlled file modification.

The resolver watch search was also performed:

```bash
sudo ausearch -k lab136_dns_resolver -i
```

The supplied output showed the Auditd rule-addition events. It did not show a subsequent write event against `/etc/resolv.conf` or `/etc/NetworkManager/`.

### 7. Validate DNS resolution

DNS resolution was checked using:

```bash
getent hosts example.com
```

The command returned:

```text
2606:4700:83b5:72db:f20d:0:ef6b:ff98 example.com
```

A DNS query was also performed:

```bash
dig example.com
```

The response showed:

- Status: `NOERROR`
- DNS server: `192.168.203.2`
- Query time: `4 msec`
- A records: `172.66.147.243` and `104.20.23.154`

These results confirm successful DNS resolution at the time of testing. They do not independently prove that the DNS server is trusted or that no prior tampering occurred.

## Key Findings

1. NetworkManager was the component generating `/etc/resolv.conf`.
2. The resolver configuration was consistent with the DNS information reported by `nmcli` for `ens160`.
3. `systemd-resolved` was not installed.
4. Auditd successfully recorded the controlled modification to the test file.
5. The SHA-256 comparison confirmed the test file contents changed.
6. The resolver and NetworkManager watches were added successfully.
7. No actual resolver configuration modification event was present in the supplied Auditd search output.
8. DNS resolution succeeded through `192.168.203.2` during validation.
9. Lab-specific Auditd watches were removed and the test directory was deleted.

## Investigation Conclusion

The lab successfully demonstrated how Auditd can record a controlled DNS-related configuration-file modification and how file hashes can establish evidence of a content change.

The active DNS resolver configuration was inspected without changing it. The observed configuration was generated by NetworkManager and used `192.168.203.2` as its DNS server.

No evidence supplied for this lab confirms unauthorized resolver modification, DNS redirection, DNS poisoning, or malicious activity.

The controlled test validates the Auditd file-monitoring workflow. Wazuh dashboard ingestion and alert generation for the controlled test were not confirmed in the available evidence.
