# Wazuh Linux DNS Resolver Tampering Investigation

## Overview

This lab investigates Linux DNS resolver configuration and examines how unauthorized or unexpected changes to DNS settings can be detected using Auditd and Wazuh.

The investigation was performed on Rocky Linux 9.8 with NetworkManager managing the DNS configuration. The primary focus was `/etc/resolv.conf`, its configuration source, file integrity, and the audit telemetry generated by a controlled file modification.

The lab also examines why DNS resolver changes must be investigated in context. A configuration change alone does not establish malicious activity because NetworkManager, DHCP, VPN software, and other legitimate components may update DNS settings.

## Repository Objectives

- Understand Linux DNS resolver configuration.
- Identify how NetworkManager manages DNS settings.
- Inspect `/etc/resolv.conf` and establish its baseline.
- Configure targeted Auditd monitoring.
- Simulate a controlled configuration-file modification.
- Compare file hashes before and after the modification.
- Investigate Auditd events to identify the process and user associated with a file operation.
- Validate DNS resolution using `getent` and `dig`.
- Understand the role of Wazuh in collecting and investigating security telemetry.

| Component | Details |

| Operating System | Rocky Linux 9.8 |
| DNS Management | NetworkManager |
| Network Interface | ens160 |
| Resolver File | `/etc/resolv.conf` |
| DNS Server | `192.168.203.2` |

## Initial Findings

- NetworkManager was active and running.
- `/etc/resolv.conf` was a regular file, not a symbolic link.
- The resolver file contained the comment `Generated by NetworkManager`.
- The configured nameserver was `192.168.203.2`.
- NetworkManager reported the same DNS server for interface `ens160`.
- `systemd-resolved` was not installed.
- Auditd was active with no pre-existing audit rules.
- Auditd initially reported `lost 0` and `backlog 0`.

## Investigation Workflow

### 1. Establish the resolver baseline

Inspect the operating system, NetworkManager service, resolver file, and active DNS configuration.

```bash
cat /etc/os-release
sudo systemctl status NetworkManager --no-pager
ls -l /etc/resolv.conf
cat /etc/resolv.conf
NetworkManager --print-config
nmcli device show
```

### 2. Inspect audit services

Check Auditd status, current audit statistics, and existing rules before introducing lab-specific monitoring.

```bash
sudo systemctl status auditd --no-pager
sudo auditctl -s
sudo auditctl -l
```

### 3. Establish file integrity baseline

Record resolver file metadata and its SHA-256 hash.

```bash
sudo stat /etc/resolv.conf
sudo sha256sum /etc/resolv.conf
```

Recorded baseline SHA-256:

```text
237d02064a9c5e5cb59347ee894eb238a2ea82e94c81d84c2969859660569cd8
```

### 4. Configure targeted Auditd monitoring

The following watches were added:

```bash
sudo auditctl -w /etc/resolv.conf -p wa -k lab136_dns_resolver
sudo auditctl -w /etc/NetworkManager/ -p wa -k lab136_dns_resolver
```

The rules were verified with:

```bash
sudo auditctl -l | grep lab136_dns_resolver
```

### 5. Perform a controlled modification

A separate test file was created under `/var/tmp/lab136` to avoid modifying the active resolver configuration.

```bash
sudo mkdir -p /var/tmp/lab136
```

```bash
sudo tee /var/tmp/lab136/resolv.conf.test > /dev/null <<'EOF'
# Lab 136 controlled DNS resolver configuration test
nameserver 192.0.2.53
search lab136.invalid
EOF
```

A dedicated Auditd watch was added:

```bash
sudo auditctl -w /var/tmp/lab136/ -p wa -k lab136_dns_test
```

The initial SHA-256 was:

```text
7ece6d4f17e33c9662d6d9d9526817bfdf8ec78ae3365bc8eb4f8da43816b61e
```

A controlled comment was appended:

```bash
echo '# Lab 136 controlled modification' | sudo tee -a /var/tmp/lab136/resolv.conf.test
```

The resulting SHA-256 was:

```text
b26119a8e32d4c46be1d179ab63133db7122b3d7e42236f3c5628b9f3960f7fb
```

The hash difference confirmed that the test file contents changed.

### 6. Investigate Auditd events

The test event was reviewed using:

```bash
sudo ausearch -k lab136_dns_test -i
```

The successful modification event contained:

- Process: `tee`
- Executable: `/usr/bin/tee`
- Operation: `openat`
- Result: `success=yes`
- File: `/var/tmp/lab136/resolv.conf.test`
- Audit key: `lab136_dns_test`
- Login identity: `abhinavmathur`
- Effective user: `root`
- Timestamp: `13/11/26 07:42:59.738`

The event confirms a successful controlled file modification.

The resolver watch search was also performed:

```bash
sudo ausearch -k lab136_dns_resolver -i
```

The supplied output showed the Auditd rule-addition events. It did not show a subsequent write event against `/etc/resolv.conf` or `/etc/NetworkManager/`.

### 7. Validate DNS resolution

DNS resolution was checked using:

```bash
getent hosts example.com
```

The command returned:

```text
2606:4700:83b5:72db:f20d:0:ef6b:ff98 example.com
```

A DNS query was also performed:

```bash
dig example.com
```

The response showed:

- Status: `NOERROR`
- DNS server: `192.168.203.2`
- Query time: `4 msec`
- A records: `172.66.147.243` and `104.20.23.154`

These results confirm successful DNS resolution at the time of testing. They do not independently prove that the DNS server is trusted or that no prior tampering occurred.

## Key Findings

1. NetworkManager was the component generating `/etc/resolv.conf`.
2. The resolver configuration was consistent with the DNS information reported by `nmcli` for `ens160`.
3. `systemd-resolved` was not installed.
4. Auditd successfully recorded the controlled modification to the test file.
5. The SHA-256 comparison confirmed the test file contents changed.
6. The resolver and NetworkManager watches were added successfully.
7. No actual resolver configuration modification event was present in the supplied Auditd search output.
8. DNS resolution succeeded through `192.168.203.2` during validation.
9. Lab-specific Auditd watches were removed and the test directory was deleted.

## Investigation Conclusion

The lab successfully demonstrated how Auditd can record a controlled DNS-related configuration-file modification and how file hashes can establish evidence of a content change.

The active DNS resolver configuration was inspected without changing it. The observed configuration was generated by NetworkManager and used `192.168.203.2` as its DNS server.

No evidence supplied for this lab confirms unauthorized resolver modification, DNS redirection, DNS poisoning, or malicious activity.

The controlled test validates the Auditd file-monitoring workflow. Wazuh dashboard ingestion and alert generation for the controlled test were not confirmed in the available evidence.

## Important Learning

A DNS resolver configuration change is an investigative lead, not proof of compromise.

A SOC analyst should establish:

- What configuration changed?
- Which user or process performed the operation?
- Was the change expected from NetworkManager or DHCP?
- Was the resulting DNS server approved?
- Did DNS resolution behaviour change?
- Is there supporting evidence of malicious redirection or communication?

**Follow the evidence, not the assumption.**
